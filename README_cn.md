# 双副牌扑克游戏平台

[English README](README.md)

这是一个基于 TypeScript、React 和 Cloudflare Worker 架构开发的双副牌扑克游戏平台。当前已实现的完整游戏是 **掼蛋**，提供单人本地游戏，以及可在本地开发环境中联机的多人房间。

## 当前功能

- 双副牌掼蛋的规则、牌型识别、合法动作校验与确定性游戏核心；
- 单人模式：1 名玩家与 3 名机器人进行本地对局；
- 多人模式：创建、加入与管理房间，支持 1–4 名真人玩家，空位由机器人补足；
- 多人实时同步、断线后的临时机器人托管，以及重新连接后继续同一牌局；
- 浏览器端牌桌与移动端基础适配。

掼蛋的具体玩法、计分与地方规则存在差异，请使用者自行参考可靠的网络规则资料。

## 单人游戏与多人游戏

| 模式     | 适用场景                         | 启动方式                           | 当前部署状态                                  |
| -------- | -------------------------------- | ---------------------------------- | --------------------------------------------- |
| 单人游戏 | 1 名真人玩家 + 3 名机器人        | 直接访问 Vercel，或本地启动前端    | 已部署到 Vercel 公网                          |
| 多人游戏 | 1–4 名真人玩家；空位由机器人补足 | 必须同时启动本地前端与本地权威后端 | 仅本地开发环境可用，尚未部署到公网 Cloudflare |

因此，Vercel 上的公开地址当前只提供**单人游戏**。多人模式虽然已在代码中实现，但必须使用本地 Wrangler/Miniflare 后端运行；不能通过 Vercel 公网地址创建或加入多人房间。

## 机器人策略现状

所有实际游戏中的机器人目前都使用 `normal-vNext`。

机器人会根据以下信息，从规则层提供的合法动作中选择出牌：

- 自己的手牌；
- 已经公开打出的牌；
- 各座剩余手牌数；
- 当前牌桌 / trick 状态；
- 规则引擎生成的合法动作。

机器人**不会读取其他玩家的隐藏手牌**。

当前策略仍属于基础启发式策略，能够处理常见跟牌、部分结构保护、队友让牌和部分尾局阻断，但尚未达到成熟人类玩家的水平。

目前仍可能出现的问题包括：

- 只看当前这一手，而没有充分考虑出牌后整副手牌的质量；
- 对不同选择的机会成本判断不足；
- 过早消耗重要的控制牌；
- 将宝贵的红桃级牌作为万能牌去组成价值很低的组合；
- 明明有更便宜的炸弹或普通出牌，却使用非常大的炸弹；
- 过早领出很强的结构，没有考虑 A、2、王等牌后续的控制价值；
- 为了保护价值不高的小结构，反而消耗更有价值的大牌；
- 做出规则上完全合法、但从正常人类玩家角度看明显不自然的选择。

## 🤖 欢迎参与机器人出牌策略优化

目前游戏引擎、规则判断和牌桌环境已经基本成熟，项目当前最开放、也最有价值的问题是：**如何提高机器人的出牌策略水平。**

目标不一定是打造职业比赛级别或理论最优的掼蛋 AI。只要能够让机器人逐步达到一个**正常普通玩家**的水平，并明显减少低级策略错误，就是非常有价值的贡献。

欢迎研究和改进的方向包括：

- 手牌态势评价；
- 候选出牌评分；
- 不同出牌方案的机会成本；
- 领牌策略；
- 跟牌策略；
- A、2、级牌、大小王等控制资源的管理；
- 红桃级牌 / 万能牌使用；
- 炸弹使用；
- 队友协作；
- 对手公开威胁判断；
- 尾局策略；
- 确定性的固定牌例 benchmark；
- 轻量级搜索或有限前瞻；
- 只使用合法公开信息的 Monte Carlo 或其他实验性方法。

其中一个最核心的问题是：

> 当机器人同时拥有多个合法动作时，应该如何衡量每种选择对未来牌局的价值和机会成本？

可能需要考虑：

- 出完当前手牌预计还需要多少手；
- 剩余散单中有多少难处理的牌；
- 对子、三张、顺子、连对、钢板等自然结构；
- A、2、级牌、王、炸弹等控制资源；
- 红桃级牌作为万能牌的弹性价值；
- 后续重新取得牌权的能力；
- 是否形成一手或两手收官路线；
- 队友当前的剩余牌数和位置；
- 对手是否已经进入临门状态。

参与策略开发**不需要重新设计游戏引擎、UI、网络或多人模式**。

请阅读 [`CONTRIBUTING.md`](CONTRIBUTING.md)，并查看 GitHub 上带有 `strategy` 和 `help wanted` 标签的 Issues。

如果你很会打掼蛋，但不想写代码，也非常欢迎提供具体牌例、你认为合理的出牌，以及人类玩家的判断理由。这类资料对后续策略优化同样非常有价值。

## 环境要求

- Node.js 22（项目声明支持 `>=22.0.0 <25`）；
- Windows PowerShell（本地多人一键脚本使用 PowerShell）；
- npm。

首次使用时，在仓库根目录安装依赖：

```powershell
npm.cmd install
```

## 运行单人游戏

### 使用公网版本

访问 Vercel 上已部署的单人游戏：

<https://card-game-wentop.vercel.app/>

### 使用本地版本

在仓库根目录运行以下命令，启动前端程序：

```powershell
npm.cmd --prefix frontend run dev
```

然后打开终端显示的 Vite 地址，默认通常为：

<http://127.0.0.1:5173/>

此方式只启动前端，适合单人游戏。

## 运行本地多人游戏

### 目前仅支持本地服务器版本

多人模式需要前端和权威后端同时运行。请在仓库根目录执行：

```powershell
npm.cmd run p4:dev
```

该脚本会启动：

- 前端：`http://127.0.0.1:5173/`；
- 本地 Worker/Miniflare 权威后端：`http://127.0.0.1:8788/`；
- 本地 SQLite-backed Durable Object 数据。

浏览器打开前端地址后，选择“多人游戏”，即可创建或加入房间。

局域网中的其他设备可访问：

```text
http://<本机 IP>:5173/
```

前端会将其 `/v1` HTTP 与 WebSocket 请求代理到运行在本机的后端。

请勿把 `8788` 端口直接暴露到局域网或公网。

正常结束时，在运行 `p4:dev` 的终端按 `Ctrl+C`。

如遇异常关闭、残留进程或端口被占用，再执行：

```powershell
npm.cmd run p4:stop
```

## 目录说明

- `frontend/`：React/Vite 浏览器应用；
- `backend/`：本地多人房间、权威 Worker 与实时通信；
- `packages/guandan-core/`：前后端共享的纯 TypeScript 规则、合法动作与机器人策略核心；
- `docs/`：规则、架构和产品说明；
- `tools/`：可复用的本地开发工具；
- `temp/`：可删除的本地中间产物，不应提交。

```powershell
npm.cmd --prefix frontend run lint
npm.cmd --prefix frontend run test:run
```

## 参与贡献

欢迎各种贡献，尤其欢迎机器人策略方面的改进。

提交策略相关修改前，请阅读 [`CONTRIBUTING.md`](CONTRIBUTING.md)。

建议每个策略 PR 尽量包含：

- 一个具体牌例；
- 当前机器人的实际行为；
- 你认为更合理的人类出牌；
- 为什么这个选择更合理；
- 对应的确定性回归测试；
- 确认机器人仍然只从合法动作中选择出牌。

请不要使用对手隐藏手牌，也尽量不要把 UI、网络或其他无关修改混在策略 PR 中。
