# 平台开发与部署路线图

> P1 已于 2026-07-15 完成并发布。本文件保留 P0/P1 的历史规划；当前 P1 实现状态、规则版本与发布限制以 `proj-info/phases/P1/phase-1-closeout.md`、`docs/resolved-rules.md` 和 `proj-info/phases/P1/release.md` 为准。

## 总体排序与理由

先完成可证明正确的单机掼蛋规则内核，再让基础机器人驱动它，随后才接 UI、PWA、联网和第二个游戏。这样可复用的不是界面，而是可测试的牌、座位、事件和插件边界；拖拉机 80 分必须是独立插件，不能用掼蛋规则改造而成。

| 阶段 | 可交付产品 | 完成后发布 |
| --- | --- | --- |
| P0 | 规则冻结与工程合同 | 文档审查，不发布运行产品 |
| P1 | 单人本地掼蛋 MVP（基础机器人） | GitHub + Vercel Hobby 生产版 |
| P2 | 移动/PWA 与策略机器人 | GitHub + Vercel Hobby 生产版 |
| P3 | 多人掼蛋（权威后端） | 前端 Vercel Hobby；实时后端按供应商能力部署 |
| P4 | 拖拉机 80 分单人插件 | GitHub + Vercel Hobby 生产版 |
| P5 | 拖拉机多人、回放与平台化 | GitHub + Vercel Hobby 前端；后端按 P3 演进 |

## P0：规则冻结和工程准备

1. 关闭 `docs/resolved-rules.md` 的 6 个待确认项；后续 P1 规则修订已演进至 `rulesVersion=guandan-v4`。
2. 为每个规则写“输入牌、等级、上手牌、预期合法动作/结算”的固定牌例。
3. 确定随机数方案（有种子、可重放）、错误码、事件词表与存档迁移政策。
4. 初始化 `frontend/`、严格 TypeScript、测试、格式化、CI 和本地开发说明。

退出条件：规则审查通过；核心类型和测试矩阵被确认；尚不实现桌面 UI 或机器人策略。

## P1：单人本地掼蛋 MVP（首次可玩发布）

### P1.1 公共最小内核

- 多副牌生成、唯一 Card ID、确定性洗牌/发牌、四座位/对家、事件日志。
- `GamePlugin`、状态快照、合法动作与玩家视图投影。
- 验收：随机 10,000 次发牌无重复/丢牌；同 seed 重放一致。

### P1.2 掼蛋规则引擎

- 全部首版牌型识别、逢人配解释、比较器、过牌、接风、完成顺序和单局结算。
- 先做首局；再做进贡、抗贡、还贡、连续升级与比赛结束。
- 验收：每条 `resolved-rules` 条款都有固定牌例；规则引擎零 UI 依赖。

### P1.3 基础机器人（难度：初级）

- 共享公共记牌：已出牌、各家剩余数、牌型/过牌历史和已出现大牌数量。
- 仅从 `BotView` 取数据；生成合法动作后按确定性启发式选择，避免无意义压队友与随意拆炸弹。
- 验收：自动 1,000 局，无非法动作、死循环、重复出牌、负牌数或不可结算状态。

### P1.4 浏览器桌面体验和本地存档

- 游戏选择页（仅启用掼蛋）、桌面牌桌、选牌/取消/提示/出牌/过牌、自动排序、设置与规则入口。
- IndexedDB 自动保存、继续/新局/清除、可重建事件与机器人公共记忆。
- 验收：刷新后恢复同一局；Chrome、Edge、Safari 的关键流程通过；无服务端依赖。

### P1.5 发布门禁

- GitHub：`feature/*` → PR → `main`；PR 必跑 typecheck、lint、unit、固定牌例和 E2E 冒烟。
- Vercel：连接已有 GitHub 仓库，Root Directory 设置为 `frontend`；分支推送产生 Preview，合并 `main` 产生 Production。
- 验收：生产 URL 可玩、刷新可恢复、Lighthouse/手工移动基线记录、回滚路径演练一次。

## P2：移动/PWA 与策略机器人（第二次发布）

### P2.1 响应式与 PWA

- 手机横屏优先，适配安全区、点击/滑动选牌、离线应用壳、升级提示。
- 缓存只缓存版本化静态资源；存档不放进 Service Worker 缓存。
- 验收：Android Chrome 与 iPhone Safari 安装/离线启动；升级后不使用旧规则引擎解释新局。

### P2.2 策略机器人（难度：普通）

- 手数/牌力评估、主攻/助攻动态角色、过牌置信度、队友意图和对手结构估计。
- `scoreAction` 按开中尾局调整权重；固定局面回归测试验证“拦对手、让队友、炸弹时机”。
- 验收：与 P1 初级机器人至少 10,000 局对测，指标和种子固化；禁止把推断升级为读取隐藏牌的事实。

### P2.3 发布门禁

- 新增触摸 E2E、离线/PWA 检查和性能预算；Preview 人工验收后合并 `main`。
- 生产发布和回归记录写入阶段日志。

## P3：多人联网掼蛋（第三次发布）

### P3.1 权威服务器与安全投影

- `backend/` 负责洗牌、完整状态、验证、机器人、超时和结算；客户端只提交意图和接收个人投影。
- 身份最小化：匿名玩家 ID + 房间码 + 可轮换重连令牌；不在 URL 或浏览器日志保存完整手牌。
- 验收：信息泄露测试证明任一客户端包不含他人手牌/随机种子。

### P3.2 房间、重连与托管

- 创建/加入/座位/准备/开始；1–4 真人、空位机器人；断线等待、机器人托管、当前动作边界后接管。
- 验收：网络中断/刷新/并发动作/过期令牌的集成测试。

### P3.3 部署决策

- Vercel Hobby 继续托管前端和静态预览。Hobby 面向个人、非商业使用，且有不能加购的用量上限；将重的实时计算、长连接和房间持久化从 Vercel 静态前端分离。
- P3 开始前做一个小型实时 POC，比较托管实时服务与独立常驻后端；以连接持续时间、房间恢复、成本和区域延迟选型。若运行后端不满足 Hobby 条款或资源上限，升级 Vercel 计划或切换后端托管，而非规避限制。
- 验收：前端仍在 Vercel Hobby；后端有健康检查、可观测日志、持久化备份、撤销/回滚流程和负载上限说明。

## P4：拖拉机 80 分单人插件（第四次发布）

1. 基于现有 `platform/` 复用牌/座位/事件/存档/UI 原语；在 `games/tractor-80/` 独立实现定主、底牌、跟牌/毙牌、墩、抠底、计分和升级状态机。
2. 先完成规则引擎与基础机器人，再接选择页、牌桌 UI 和本地保存。
3. 验收：掼蛋全套回归保持通过；80 分规则每项有牌例；单人 1,000 局稳定；发布至同一 Vercel 项目。

## P5：平台化收尾

- 拖拉机多人、跨游戏回放浏览、无障碍/国际化、观战和账号等按价值单独立项。
- 高级机器人（难度：高级/专家）作为独立研究里程碑：隐藏手牌采样、受限蒙特卡洛和深度搜索必须在 Web Worker/后端预算中运行，并用固定 seed、时间上限、胜率提升和信息边界测试验收。

## 每次发布的统一核对表

1. `main` 仅合入已审查 PR；版本号、规则版本和变更记录同步。
2. CI 通过：typecheck、lint、单元、固定牌例、随机自动局、E2E 冒烟。
3. Preview 手工验证：新局、出牌、过牌、存档恢复、异常提示。
4. 合并 `main` 后由 Vercel 创建生产部署；记录 URL、commit、构建日志和验证结果。
5. 失败时优先回退到上一生产部署，再诊断；不得在生产环境热改规则。
