# ADR-0016：P2.5 专家启发式机器人契约与性能预算

- 状态：已接受
- 日期：2026-07-16
- 决策人：产品负责人
- 关联：ADR-0008（`BotView` 信息边界）、ADR-0009（基础机器人历史 tie-break）、ADR-0014（公开观察模型）、[P2.5 实施计划](../phases/P2.5/implementation-plan.md)

## 背景

P2.5 的目标是让机器人先组牌，再判断是否值得争牌，并评价动作后的整手牌、控制资源和至少下一手路线。P2.5-01 审计确认：现有规则合法性与 `BotView` 公平边界正确，但候选生成、组牌、动作后评估、争夺价值和公开事件消费尚未形成独立契约。

若把这些能力重新塞入单一评分函数，或以墙钟超时限制搜索，会破坏可解释性、可复现性和后续策略扩展能力。本 ADR 冻结各模块的只读输入、输出、版本、性能预算与统计归属；不改变任何掼蛋规则、事件 schema、存档 schema 或现有机器人行为。

## 决策

### 1. 不可变边界

1. 规则引擎仍是唯一合法性裁决者：策略只能在 `BotView.legalActions` 中选择。候选补全可提议动作，但必须经现有 `getLegalActions` / `validateAction` 过滤；提交后仍由 `applyAction` 执行。
2. P2.5 分析器只接收 `BotView`、显式的只读 profile 快照和由这些输入派生的结果。禁止读取对手真实手牌、牌堆、洗牌顺序、seed、全局 `TurnState`、调试真值或其他机器人隐藏评估。
3. 相同的 `BotView`、profile 快照、策略/权重版本和规则版本，必须在冷缓存、暖缓存、同步路径和 Worker 路径产生相同候选、计划、分项、规则命中、解释和最终动作。不得按墙钟时间截断搜索。
4. `DecisionExplanation` 是派生诊断数据。它不得写入 `TurnState`、事件流、快照、IndexedDB 存档或网络协议；关闭解释详情只能省略文本/快照，不能改变分数或选择。
5. P2.5 是专家启发式，不是搜索深度竞赛。有限计算资源优先用于高质量整手组牌、动作后重新评估和专家规则评分；避免枚举大量质量接近或收益很低的候选。未来预算调整不得要求重构算法，也不得改变游戏规则。

### 2. 决策链与模块责任

```mermaid
flowchart LR
    A[规则引擎合法动作] --> B[HandStructureAnalyzer]
    B --> C[HandPlanGenerator]
    C --> D[SituationAnalyzer]
    D --> E[ContestEvaluator]
    E --> F[ActionFeatureExtractor]
    F --> G[PostActionHandEvaluator]
    G --> H[ControlResourceEvaluator]
    H --> I[FollowUpPlanner]
    I --> J[ExpertStrategyKnowledgeBase]
    J --> K[ActionScorer]
    K --> L[ActionSelector]
    L --> M[DecisionExplanation]
```

`HandStructureAnalyzer`、`HandPlanGenerator`、`SituationAnalyzer` 和后续动作级模块不得互相修改输入；后者只能消费前者已命名的输出。允许为减少重复读取把 `ContestEvaluator` 分为“局面级 contest context”和“动作级 contest result”，但不得把全部职责合并为巨型评分函数。

| 模块                              | 只读输入                                   | 输出与禁止事项                                                                                 |
| --------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `HandStructureAnalyzer`           | `selfHand`、`levelRank`                    | 实体牌归属、天然/逢人配完成/拆已有组来源、可用结构、散牌、控制与回收资源；不判断动作是否合法。 |
| `HandPlanGenerator`               | `HandStructure`、profile 预算、已知 role   | 稳定排序的整手方案；不枚举无限分组，也不选择当前动作。                                         |
| `SituationAnalyzer`（P2.5-06）    | `publicEvents`、余牌数、座位、当前公开牌局 | 阶段、公开关键牌、威胁、队友状态、角色与置信度；不反查隐藏信息。                               |
| `ContestEvaluator`                | `Situation`、计划摘要、动作级结构/资源成本 | 是否值得争牌及可解释收益/成本；不以“有合法压制”强制接牌。                                      |
| `ActionFeatureExtractor`          | 合法动作与上述派生结果                     | 统一动作特征，引用而非重算分析器。                                                             |
| `PostActionHandEvaluator`         | 当前结构/计划、候选动作、重组预算          | 移除实体牌后的手牌质量差值；不修改原手牌或规则状态。                                           |
| `ControlResourceEvaluator`        | 结构、局面、动作后结果                     | 王、级牌、红桃级牌、A、高对子/三张、炸弹和同花顺的预算、机会成本与例外。                       |
| `FollowUpPlanner`                 | 动作后手牌、局面、合法领出候选上限         | 至少一手的路线/无路线结论；不假设对手隐藏出牌。                                                |
| `ExpertStrategyKnowledgeBase`     | 特征快照、profile                          | 结构化加减分、硬排除/例外和证据；不直接调用规则引擎或写状态。                                  |
| `ActionScorer` / `ActionSelector` | 统一特征、规则调整                         | 分项总分和稳定 tie-break；只返回原 `legalActions` 的元素。                                     |

### 3. TypeScript 契约草案

以下为实现前的结构草案，类型名可在 P2.5-04 之后按仓库既有命名落地；字段语义和只读边界不得收窄。

```ts
type StrategyProfileId = "normal" | "expert" | "experimental";
type EvidenceLevel =
  "rules_based" | "expert_source" | "heuristic" | "needs_expert_validation";
type StrategyMaturity = "default_eligible" | "experimental";

interface StrategyProfileSnapshot {
  readonly id: StrategyProfileId;
  readonly version: string;
  readonly rulesVersion: string;
  readonly weightsVersion: string;
  /** 由 profile/config 加载；不是算法内联常量。 */
  readonly performanceBudget: PerformanceBudget;
  readonly enabledRuleIds: readonly string[];
}

interface SearchLimit {
  readonly default: number;
  readonly max: number;
}
interface PerformanceBudget {
  readonly handPlanTopN: SearchLimit;
  readonly postActionReplanCount: SearchLimit;
  readonly followUpCandidateCount: SearchLimit;
}
function followUpCandidateLimit(
  budget: PerformanceBudget,
  legalLeadActions: readonly TurnAction[],
): number {
  return Math.min(
    budget.followUpCandidateCount.default,
    budget.followUpCandidateCount.max,
    legalLeadActions.length,
  );
}

type StructureSource =
  "natural" | "wildcard_completed" | "split_from_existing_group";
interface HandStructure {
  readonly fingerprint: string; /* groups and resource inventory */
}
interface HandPlan {
  readonly id: string;
  readonly metrics: HandPlanMetrics;
}
interface Situation {
  readonly publicEventSequence: number;
  readonly threat: ThreatAssessment;
}
interface PostActionHandEvaluation {
  readonly actionId: string;
  readonly delta: HandQualityDelta;
}
interface FollowUpPlan {
  readonly actionId: string;
  readonly noUsefulFollowUp: boolean;
}

interface ExpertBotModules {
  analyzeHand(view: BotView): HandStructure;
  generateHandPlans(input: {
    readonly structure: HandStructure;
    readonly profile: StrategyProfileSnapshot;
  }): readonly HandPlan[];
  analyzeSituation(view: BotView): Situation;
  evaluatePostAction(input: {
    readonly view: BotView;
    readonly action: TurnAction;
    readonly structure: HandStructure;
    readonly plans: readonly HandPlan[];
  }): PostActionHandEvaluation;
  planFollowUp(input: {
    readonly view: BotView;
    readonly action: TurnAction;
  }): FollowUpPlan;
}

interface StrategyRuleDefinition {
  readonly id: string;
  readonly evidence: EvidenceLevel;
  readonly maturity: StrategyMaturity;
  readonly appliesTo: readonly StrategyProfileId[];
  readonly evaluate: (
    input: Readonly<ActionFeatureSnapshot>,
  ) => readonly RuleAdjustment[];
}

interface ExpertBotDecision {
  readonly selectedAction: TurnAction;
  readonly explanation: DecisionExplanation;
  readonly decisionFingerprint: string;
}
```

P2.5-03 负责使 fixture 能表达上述输入/预期，不实现模块。P2.5-04 只实现 `HandStructure` 与来源归属；它不生成全手计划、也不评估公开局面。P2.5-06 只把公开事件转换为 `Situation`，并输出可解释置信度；它不能从缓存或任何状态取得隐藏信息。`HandPlanMetrics`、`ThreatAssessment`、`HandQualityDelta`、`ActionFeatureSnapshot` 与 `DecisionExplanation` 的完整字段在各自实现任务以本 ADR 的责任边界补全。

### 4. 信息投影、稳定性与缓存

`BotView` 的现有字段是唯一事实输入。`publicEvents` 必须是按已应用顺序累计的公开事件；`publicEventSequence` 是该数组最后一个已消费事件的序号（无事件为 `0`）。模拟器在 P2.5-16 必须以同一投影累计它，不能以空数组替代。

所有跨回合缓存键均使用完整 `DecisionFingerprint`：排序后的己方实体牌 ID、`levelRank`、公开事件序号、四席余牌数、`leader`、`highestSeat`、当前最高牌的公开比较摘要、profile/version、规则版本和权重版本。缓存命中与冷计算必须逐字段等价。

- `HandStructureCache`：手牌实体 ID + 级牌；允许复用相同或高度相似手牌的不可变索引/中间分组，但最终结构必须由完整指纹确认。
- `HandPlanCache`：结构指纹 + profile/version + role；复用候选索引和中间评分，不得把不同 profile 的方案混用。
- `PostActionCache`：动作后手牌指纹 + 动作 ID + profile/version；只能复用无副作用的分析结果。
- `FollowUpCache`：动作后手牌指纹 + 领出公开状态 + profile/version；事件序号或当前赢家变化即失效。

缓存是性能优化，不是策略语义。跨回合缓存必须设置容量上限和可观测的命中/失效计数；P2.5-16 负责实现和基准。不得使用近似缓存结果直接决定动作。

### 5. 可配置性能预算、候选上限与确定性早停

以下数值是 profile 的 `PerformanceBudget` 默认值/硬上限，属于可版本化配置，非游戏规则常量。未来可在固定牌例、自动对局和性能数据支持下调整，不需重构分析器或评分器：

| 项目                         |                        默认 | 最大值 | 约束                                   |
| ---------------------------- | --------------------------: | -----: | -------------------------------------- |
| `HandPlan` Top-N             |                           8 |     16 | 稳定排序后仅保留 Top-N；不得全局穷举。 |
| `PostAction` 重组方案数      |                           5 |      8 | 每动作后只重组固定数目的高质量方案。   |
| `FollowUpPlanner` 领出候选数 | `min(10, LegalLeadActions)` |     16 | 只评估稳定排序的高价值合法领出候选。   |

候选、计划和路线都必须先按明确质量键与稳定 ID 排序，再应用上限。预算由版本化 profile/config 加载；表中的默认值是新 profile 的配置默认，不是算法内联常量。配置必须校验 `0 < default <= max`；不合法配置使 profile 不可加载，不能回退到隐式默认值。`FollowUpPlanner` 实际上限为 `min(followUpCandidateCount.default, followUpCandidateCount.max, LegalLeadActions.length)`。

当前回合的 `legalActions` 是规则引擎已裁决的完整集合，不得因性能预算而删掉合法动作或让策略自造未验证动作。P2.5-07 对每个组牌方案生成的高质量动作、P2.5-08 的动作后重组和 P2.5-10 的后续领出，分别受本节的 Top-N、重组和 follow-up 上限约束；任何新增“主动作评分候选”截断参数都必须先作为 `PerformanceBudget` 的版本化字段写入 ADR，不能硬编码在策略中。

允许确定性 `Early Stop`：仅当已评估方案的评分下界严格高于所有未评估方案根据质量上界可达到的上界时，才停止后续计划/候选；记录 `bound_proven` 及其上下界。不得因已耗时、设备速度或随机顺序提前停止。对于质量接近或界限不可证明的候选，必须继续到配置上限。

基础/普通/专家策略 CPU 计时分别以单次决策为样本，不含 UI 可见等待、渲染、I/O 或 Worker 排队。门槛为基础平均 `<=10ms`，普通平均 `<=30ms` 且 P95 `<=75ms`，专家平均 `<=100ms` 且 P95 `<=250ms`。P2.5-16 必须同时记录桌面/移动、冷/暖缓存、样本量与硬件；P2.5-17 才根据预先冻结的样本设定发布阈值。仅当真实移动端主线程卡顿、掉帧或专家 P95 超标时才评估 Web Worker；Worker 输入输出必须可序列化、带决策指纹、过期即丢弃，并与同步路径等价。

### 6. 9 项专项指标及统计归属

P2.5-16 的模拟器/基准层是所有聚合分子、分母、seed、profile/version、缓存状态与耗时的唯一统计归属；分析器和策略规则只输出可审计标志，不在业务模块内累加全局计数。直接出完动作不计入“动作后”类分母，除非定义明确要求。

| 指标                     | 分子                                                  | 分母                 |
| ------------------------ | ----------------------------------------------------- | -------------------- |
| 无必要拆天然炸弹率       | 存在合理合法且不拆天然炸弹替代时仍拆炸的动作          | 对应机会             |
| 逢人配低价值使用率       | 逢人配用于低对子/低炸弹，且无直接出完或高威胁阻断收益 | 使用逢人配的动作     |
| 有自然炸弹仍制造小炸弹率 | 保有天然炸弹却以逢人配制造更小炸弹                    | 对应机会             |
| 手牌较多时控制牌耗尽率   | 余牌高于阶段阈值且动作后控制资源为零                  | 可使用控制资源的机会 |
| 动作后低散单增加率       | 动作后 2—7 低散单增加                                 | 非直接出完动作       |
| 高成本无意义压制率       | 低威胁、高结构/资源成本、无有用后续仍压制             | 可过牌争夺机会       |
| 高 DeadHandRisk 形成率   | 动作后从未高风险跨入高风险                            | 非直接出完动作       |
| 队友压住时无意义接牌率   | 队友已压住、无高威胁接管理由仍接牌                    | 可合法让牌机会       |
| 尾盘阻断成功率           | 面对高威胁对手，成功延迟其出完                        | 可合法阻断机会       |

“合理替代”“低价值”“高威胁”“高成本”“控制资源”“高风险”和“成功延迟”必须引用版本化策略/分析阈值，并把命中的规则、例外和证据写入该局诊断记录。P2.5-17 冻结发布阈值前不得用胜率替代任何一项指标；八个阻断牌例必须零失败。

### 7. profile、证据、成熟度与回滚

`normal`、`expert`、`experimental` 是独立、版本化 profile：

- `normal`：既有策略的回归/对照/调试基线，不静默继承专家规则。
- `expert`：P2.5A 验收后机器人与提示的默认 profile，只加载 `default_eligible` 规则。
- `experimental`：隔离实验规则和预算，永不成为默认值。

`evidence` 与 `maturity` 相互独立。`experimental` 成熟度的规则只能进入 `experimental` profile。`needs_expert_validation` 规则可进入 `expert` 的前提是同时有明确牌理说明、至少一个固定牌例、命中/未命中/例外测试、不与冻结规则冲突、自动对局和回归未发现明显异常、可由 profile 单独关闭、且 `DecisionExplanation` 显示证据等级。任何一项失效都必须降为 `experimental`，或从 profile 的 `enabledRuleIds` 移除；这不是第三种 `maturity` 语义。

规则注册表按稳定 `id` 排序并拒绝重复 ID；profile 保存规则集版本、权重版本、预算版本和启停快照。策略/profile 升级不改变事件或存档语义；回滚仅切换到已记录的 profile 快照，不能重解释旧存档，也不能把解释写入存档。

## 后果

- P2.5-03 依据该 ADR 设计固定牌例 schema，明确 fixture 所需的公开局面、profile/version、预期特征、推荐/拒绝动作及解释断言。
- P2.5-04 先实现可复用、无副作用的手牌结构与实体牌来源；P2.5-05 才在其输出上生成受预算约束的 Top-N 方案。
- P2.5-06 只能消费累计公开事件并产出 `Situation`，为后续争夺/协作提供可解释输入，不能扩大 `BotView`。
- P2.5-07 至 P2.5-15 的实现必须保持本 ADR 的只读边界、稳定排序、profile 隔离和解释持久化限制。
- P2.5-16 实现缓存、Early Stop、模拟器公开事件和指标聚合；在此之前不得宣称专家性能达标。

## 验证

后续至少验证：

1. 类型/导入审计证明策略模块无法接收对手手牌、seed 或完整游戏状态；最终选择属于 `legalActions`。
2. 冷/暖缓存、增量/全量、同步/Worker 的决策指纹、候选、分数、解释和动作完全一致。
3. 任一手牌、级牌、公开事件序号、余牌数、公开赢家、profile/规则/权重版本改变都会正确失效缓存。
4. 配置上限、稳定排序和 `bound_proven` Early Stop 可被单测；墙钟或设备速度不改变选择。
5. 9 项指标可重放至具体动作、规则版本和 seed；固定严重牌例零失败。
6. `experimental` 规则不能进入默认 `expert`，且 `needs_expert_validation` 的七项资格门禁均可独立测试。
